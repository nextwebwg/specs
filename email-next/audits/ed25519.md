# Ed25519 signatures

[RFC8032](https://www.rfc-editor.org/rfc/rfc8032.html) defines the Ed25519 signature scheme selected by the Email Next security profile. A valid signature proves a relationship between a key and exact message bytes. Establishing who may use that key remains the responsibility of the identity and conversation rules.

## The selected variant

The baseline uses **plain Ed25519**, with a 32-octet public key and a 64-octet signature consisting of encoded R followed by S. Its prehash function is the identity function and its algorithm context is empty. SHA-512 is used internally; this does not turn the scheme into Ed25519ph. Ed25519ctx, Ed25519ph, Ed448 and Ed448ph are not enabled by this review.

[RFC9420 Section 5.1.2](https://www.rfc-editor.org/rfc/rfc9420.html#section-5.1.2) requires the group's signature scheme to match its credentials and KeyPackages. Suite `0x0001` selects `ed25519`. MLS signs its encoded `SignContent`, including the `MLS 1.0 ` label, using that scheme. Email Next's detached binding and possession proofs instead sign their own fixed-purpose prefix, length and exact payload bytes. Neither construction selects Ed25519ctx: these labels are bytes in the signed message, not the algorithm's context parameter. The detached proof must not replace MLS framing or signatures.

The inspected `binding-signature.mjs` helper requires an Ed25519 private key and calls Node's signing and verification APIs with a null digest selection. Its verification path requires exactly 32 public-key octets and 64 signature octets, represented by canonical lowercase hexadecimal. Signature validity alone does not authorize enrollment, account continuity or message release.

## Verification and implementation boundaries

Sections 5.1.2–5.1.7 define compressed point encoding, decoding failure and the scalar range `0 <= S < L`. Implementations must reject invalid encodings and out-of-range scalars. An application must not weaken those checks to accept a proof that its cryptographic library rejected.

RFC8032 permits cofactor-multiplied verification and a sufficient alternative without that multiplication. Section 8.8 explains that their acceptance behavior can differ. This audit does not establish that the project's Node and MLS libraries accept exactly the same unusual inputs. Additional implementation evidence would be needed for that claim; the held edge-case-vector proposal does not itself settle the policy.

Deterministic signatures still require secure randomness for key generation. Secret-dependent timing, memory accesses and arithmetic remain library concerns. The RFC's Python examples expressly lack production side-channel protections and are not used as a replacement implementation. Prehashing a message to avoid buffering would change what is signed and cannot silently replace the selected scheme.

No vectors or sample programs were executed in this review. Existing application tests are separate evidence, not a complete RFC8032 implementation certification. The selected [SHA-512 requirements](sha256.md#sha-512-inside-ed25519) have a separate source review. Entropy and underlying library assurance remain distinct from these source reviews. Reviewing Ed448 and its SHAKE-based construction does not add either to the Email Next profile.
