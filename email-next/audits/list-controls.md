# Mailing-list controls audit

**Coverage:** complete fifteen-page [RFC 2369](https://www.rfc-editor.org/rfc/rfc2369.html), including appendices A and B, references and end matter. No matching errata appear in the retrieved RFC Editor dataset. Modern URL and mailto dependencies remain open.

## Finding

Email already has declarative commands that clients can render as buttons. The fields carry destinations and command data, not trusted executable code. They do not define a general form language or authorize actions merely because a message was opened.

| 2 | Angle-bracket URL alternatives ordered left to right; choose one supported method, another only after failure. Senders must not insert internal whitespace; clients ignore it. ## Email Next consequence

Use these fields for list-specific controls, separate from authenticated conversation membership or form events. Never infer encryption authority from List-Owner or list membership from List-Subscribe. No command fires on preview, rendering, focus or link scanning. Offer the user a reviewable destination, account and action before sending a mail command.

Keep RFC 8058 one-click handling separate: it adds authenticated headers and a particular consented POST contract. An arbitrary List-Unsubscribe URL is not that contract. Do not execute multiple alternatives concurrently or substitute local account data into an invented template language.

## Verification boundary

Required cases include comments and folded whitespace, multiple alternatives, malformed tails, duplicate fields, List-Post NO, nested lists, unsafe schemes, ambiguous sending accounts, mailto review and cancellation, and rendered controls that perform no network action. No live list service or independent client test is claimed.
