# Mailing-list identity audit

**Coverage:** complete nine-page [RFC 2919](https://www.rfc-editor.org/rfc/rfc2919.html), including examples and end matter. Verified erratum 3951, held-for-update erratum 2499 and rejected erratum 361 reviewed.

## Finding

List-Id is a stable organizational hint with case-insensitive equality. Its descriptive name can change without changing list identity. It is not a cryptographic group identifier, a recipient roster or proof that a message came from the named list.

| Section | Disposition |
| --- | --- |
| 1 | Stable list identity supports filtering across changes to submission address or host; it is not a conversation or membership identifier. |
| 2 | Domain namespace allocation requires authority; unmanaged localhost namespace is allowed. Identifier limit255 octets. Grammar uses dot-atom-text rather than imposing hostname resolution. Held2499 identifies DRUMS reference as2822. |
| 3 | At most one List-Id, generated by list software; optional descriptive phrase is separate from bracketed identity. Ignore internal whitespace on reception, never insert it on generation. Verified3951 permits phrase or CFWS before bracket; Rejected361 does not make field names case-sensitive. |
| 4 | Prefer stable identifier across hosting changes; changed identifier is normally a different list. Description changes alone do not change identity. |
| 5 | Managed identifiers must be globally unique; unmanaged localhost identifiers cannot guarantee uniqueness. Historical random/date construction is naming guidance, not authentication. |
| 6 | Only defined operation is case-insensitive equality of bracketed identifier, excluding descriptive phrase. Do not infer DNS endpoints or credentials from it. |
| 7 | Aware nested lists preserve parent List-Id; unexpected or user-originated fields should not pass through. Therefore a field alone cannot enumerate distribution paths or recipients. |
| 8 | Forged fields can mislead processing; List-Id should not establish message authenticity. Email/2 additionally prohibits using it as cryptographic membership authority. |
| 9 | Acknowledgements reviewed. |

## Email/2 consequence

Use list identity to organize legacy list mail without collapsing every list message into one conversation. Preserve message-level reply references and original source. Display-name changes must not create a new list solely because the optional phrase changed.

A different identifier is not automatically an authenticated migration of the old list. A known List-Id in forged mail must not authorize membership changes, key replacement, history disclosure or interaction execution. An aware sublist may retain its parent's identifier, so do not infer a complete delivery audience from the field.

Required cases include case-only identifier differences, changed descriptive phrases, allowed pre-bracket whitespace, internal whitespace tolerance, duplicate fields, a changed identifier, unmanaged-name collisions, spoofed identifiers and nested lists. This review does not claim a complete List-Id parser or real-list interoperability test.
