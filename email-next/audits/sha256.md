# SHA-256 and SHA-512 hash primitives

The selected MLS suite uses SHA-256 as defined by [FIPS180-4, August 2015](https://doi.org/10.6028/NIST.FIPS.180-4). The hash produces a 32-octet digest of exact input bytes. It does not authenticate a sender on its own; MLS, HMAC and the application's authenticated records supply their respective security context.

## Selected requirements

SHA-256 uses 512-bit message blocks, 32-bit words, big-endian encoding and arithmetic modulo 2³². Its specified padding includes the original bit length; its eight initial words, 64 round constants, message schedule and compression steps are fixed. Implementations may use equivalent computation methods that produce identical results. Email/2 delegates this primitive to established libraries rather than defining another implementation.

The primitive accepts bit lengths below 2⁶⁴. That mathematical bound does not replace the smaller limits on Email/2 records, MIME messages, HKDF inputs or cryptographic-library APIs. Application code must supply the exact bytes required by the enclosing protocol without normalizing text or adding its own hash padding.

A 256-bit result from another algorithm is not interchangeable with SHA-256. In particular, SHA-512/256 uses different processing and initial values. The standard's generic truncation discussion does not permit shortening the selected digest or MLS tag. SHA-512's use inside Ed25519 is also distinct from SHA-256 in the selected MLS hash and KDF.

## SHA-512 inside Ed25519

The selected [Ed25519 signature algorithm](ed25519.md) also depends on SHA-512. This is a distinct use from SHA-256 in MLS and HKDF. FIPS180-4 sections 4.1.3, 4.2.3, 5.1.2, 5.2.2, 5.3.5 and 6.4 define the applicable functions, constants, preprocessing and computation.

SHA-512 processes 1024-bit blocks using 64-bit words, arithmetic modulo 2⁶⁴, 80 round constants and eight fixed initial words. It appends the original bit length as a 128-bit value and emits all eight final words as a 64-octet digest. Its input length must be below 2¹²⁸ bits; enclosing protocol and library limits still apply.

The signature library must hash the exact inputs prescribed by Ed25519. Application code must not replace pure Ed25519 with signing a separately computed SHA-512 digest: that changes the signature input and is not Ed25519ph either. SHA-384 and SHA-512/t are not substitutes. SHA-512's internal word encoding does not change Ed25519's specified scalar encodings.

## Publication status and corrections

The [official publication page](https://csrc.nist.gov/pubs/fips/180-4/upd1/final) identifies the August 2015 edition and links a planned revision. NIST's [revision decision](https://csrc.nist.gov/news/2023/decision-to-revise-fips-180-4) calls for removing SHA-1, incorporating applicable hash-use guidance and improving references and presentation. A revision announcement is not a replacement algorithm definition.

The captured PDF includes an incorporated editorial erratum dated 9 May 2014, correcting the SHA-1 function range to include round 79. It does not change SHA-256. The publication page did not list another errata attachment when checked on 20 October 2026; this is an observation of the cited sources, not a guarantee that no other issue exists.
