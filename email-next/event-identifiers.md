# Event identifiers and exact references

This chapter selects identifier and reference rules for the experimental Email Next event format. These are proposed protocol choices, not registered URI schemes or approved standards. They replace the previously open identifier grammar; the [encoding contract](event-encoding.md) selects exact-byte serialization identity, while the complete event schema and cryptographic binding remain separate work.

## Identifier grammar

A conversation, event, form, field or choice identifier is a string of exactly 32 lowercase hexadecimal characters representing 16 bytes generated by a cryptographically secure random generator. The all-zero value is invalid. Generators MUST generate a new identifier for each new object and preserve it for retries of that object. They MUST NOT encode an address, timestamp, device fingerprint or content digest into these identifiers.

Identifiers are opaque and compared byte-for-byte. No trimming, case folding, Unicode normalization or numeric conversion is permitted. Uppercase hexadecimal, prefixes, separators, non-ASCII characters and alternate encodings are invalid. A malformed identifier MUST NOT be repaired into an accepted one.

This grammar is an experimental design choice. It uses 128 random bits for distributed generation without a central allocator. It does not claim that random identifiers authenticate content, hide traffic relationships or make collisions impossible. Conflicting authenticated content is handled by the interaction conflict rules even if a collision is accidental.

## Scope

An event's deduplication key is the pair of its authenticated principal identifier and event identifier. The principal identifier is supplied by the selected security profile and is not inferred from the event's claimed mailbox. Reusing an event identifier under the same principal for different content, conversations or operations is a conflict, not a new namespace.

A conversation identifier groups contributions but grants no access. Equal identifiers do not prove that two recipients possess the same history. The initial form event establishes the form identifier under that event's authenticated author. Field identifiers are scoped to that form; choice identifiers are scoped to their field. Revisions preserve identifiers only where the interaction contract permits meaning to remain continuous.

Each form revision has its own event identifier. The revision's identity is the complete event reference below; a revision counter or date is not a substitute. A submission names the form authority, form identifier and exact revision event. A field or choice identifier alone cannot identify a question outside that context.

## Exact event reference

The experimental JSON representation of an event reference has exactly three members:

| Member | Value |
| --- | --- |
| `principal` | Opaque principal identifier under the security profile used by the referring event |
| `event` | Event identifier using the grammar above |
| `conversation` | Conversation identifier using the grammar above |

All three members are required strings. Duplicate member names, additional members and null values are invalid. The [security profile](security-profile.md#account-and-device-identifier-encoding) defines the experimental account-principal encoding; implementations MUST apply that encoding and its exact comparison rules. A mailbox string is not an acceptable stand-in. A reference MUST NOT be accepted solely because its principal string matches an unverified claim.

A reference is covered by the referring event's authentication. This binds the author's claimed relationship; it does not authenticate the referenced event. The receiver separately validates that event and confirms that its authenticated principal, event identifier and conversation identifier match the reference exactly.

The receiver resolves only from content it is authorized to access. A reference MUST NOT trigger an external URL fetch, search other users' mailboxes or solicit content from a third party automatically. A missing target remains pending. A conflicted target remains conflicted. A target in a different conversation is invalid for the baseline answer/replacement operations; forwarding requires its own explicit semantics.

## Retries, revisions and collisions

A transport retry retains the event identifier and the exact authenticated event representation. It may change outer transport fields or MIME transfer encoding where the selected protection profile permits that change. It MUST NOT change the event's audience, operation, target or content under the same identity.

Editing an unsent draft does not create an event identity visible to recipients. Sending freezes the contribution. A later user correction creates a new event and explicit replacement references; it does not reuse the prior event identifier. If a retry requires a material change, prepare a new contribution and handle the original delivery uncertainty explicitly.

An unauthenticated message cannot reserve an authenticated principal's identifiers. When distinct authenticated records collide, retain the evidence and suppress effects from the conflicted identity as described in the interaction contract. Never resolve a collision by generating a replacement identifier on receipt: doing so would change what the sender authenticated.

## Ordinary email identifiers

> [!ex] The same Message-ID on two different messages
> Alice's original email and a modified copy might arrive with the same outer Message-ID. A client may use that value to suggest a thread, but it must not use it to decide that the modified copy is Alice's authenticated original.

Email Next uses ordinary Message-ID, In-Reply-To and References fields for legacy navigation. They MUST NOT substitute for an authenticated event reference, reserve a principal's event namespace or authorize an edit. ENVID tracks a transport submission; it is not a contribution identifier. [RFC5598 §3](https://www.rfc-editor.org/rfc/rfc5598.html#section-3) provides the architectural distinction; the applicable message-format and delivery-status specifications remain authoritative for wire syntax.

For a newly authored correction, generate a new outer Message-ID as well as a new event identifier. Where a known original mail copy is referenced, its Message-ID may appear in ordinary reply headers. Preserve the structured reference independently. An absent or ambiguous outer identifier does not justify guessing that reference, and a valid structured reference does not make an unverified outer address authoritative.

## Display references are separate

A local range, HTML element identifier or RFC5147 text fragment can help show the passage associated with an answer. It MUST NOT replace the exact event/form/revision/field reference. A stale display location can fail without changing the structured answer's target. Conversely, finding the same words elsewhere cannot repair an invalid structured target.

## Validation evidence

The identifier experiment validates the selected ASCII grammar and uses a cryptographic random generator. It does not implement principal encoding, complete event serialization, cryptographic authentication or persistent collision handling. Those dependencies remain required before this chapter provides interoperable event references.
