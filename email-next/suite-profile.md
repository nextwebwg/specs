# Protected conversation agreement

New Email/2 Encryption clients implement `mail-conversation-v2`, the asynchronous protected agreement. One authored message can reach independently ready recipients through several encrypted deliveries and still appear once in the conversation. Explicit reply destinations, identifiable new writing and quotations, encrypted personal addresses and both required rendering profiles are part of that agreement.

Every protected client can safely read its fixed contribution vocabulary. Answer buttons, reaction controls, corrections, service submissions and hosted-reply processing are independently implemented interactions. A simpler client can read a question and write a permitted reply without providing its answer buttons. Basic providers and clients that do not claim Encryption retain their own module obligations.

This is the current selection within one unpublished Email/2 specification, not a claim that a complete implementation or independent interoperability has been demonstrated. Earlier experimental encodings retain their exact recorded schemas and evidence scope. The [module framework](modules.md) owns adoption and indicator semantics; optionality cannot remove a claimed module's safety requirements.

## Current client baseline

An Encryption claim requires the complete asynchronous agreement below, not a parser, tuple name or older experiment. It uses the same MLS protocol and cipher suite as the earlier agreements; this selection defines the conversation behavior, not another encryption-strength level or edition of Email/2.

## Asynchronous protected agreement

`mail-conversation-v2` is the selected agreement for authored messages delivered to independently ready recipients. It combines [authored0, envelope6 and slot reply-intent1](event-encoding.md#asynchronous-authored-records-and-deliveries) with the exact native and carrier binding below. Its [automatic acquisition](first-contact-setup.md#acquisition-for-independently-ready-deliveries) is specified; the [ongoing own-device setup exchange](paired-configuration.md#keep-setup-current-between-your-own-devices) and the [pending-send lifecycle](delivery-policy.md#complete-a-pending-delivery) are selected. It is the current draft baseline. Implementation and independent acceptance remain separate requirements; mail-conversation-v1 and earlier encodings keep their exact meanings.

This is an interoperability binding within the same unpublished Email/2 specification, using the existing MLS version and cipher suite. Its internal record numbers do not name another product edition or a stronger encryption level.

Everyone implementing this agreement can read its finite vocabulary of contributions. Optional capabilities determine which interactions that particular client implements. Carol can read Alice’s question and write a normal reply while Bob can also press an answer button. Carol’s missing button feature does not require a different authored message or prevent Bob from answering.

The [fixed application example](examples/async-application.json) is the same for Alice, Bob and Carol. Their [synthetic per-device offers](examples/async-reading-offers.json) differ only in implemented interactions. They are offer objects, not complete signed assertions or evidence of client support. Alice’s [known question](examples/async-readable-question-authored.json) has identical original bytes in Bob’s and Carol’s delivery records; Carol’s [ordinary reply](examples/async-simple-reader-reply-authored.json) targets that logical question without claiming a button submission.

A sender can begin with a valid ready delivery. The agreement is checked against that delivery’s actual selected devices, not against a fictitious encrypted roster containing every pending slot. Each remaining delivery independently obtains the required setup and passes its current release checks. No intended person is silently omitted from the authored message.

### Attachment names on receipt

An independent attachment still requires exactly one syntactically valid `Content-Disposition` header with disposition `attachment`. Generators include exactly one logical filename, using the [filename projection and MIME parameter encoding](messages.md#mime-filename-projection). A valid RFC2231 continuation supplies that one value through several numbered parameters; it is not several filenames.

For mime-suite-v2 receiving only, an absent or unusable filename is a metadata diagnostic, not by itself a carrier-selection failure. Preserve the original header and report the filename as unavailable when its continuations have a missing, repeated or leading-zero index, its encoding cannot be decoded, or plain, extended or continued forms compete. Repeated physical filename parameter names are included in this diagnostic rule, even if their values agree. Parameter names are compared without case sensitivity, and continuation indices by numeric value; no first-wins or last-wins choice repairs ambiguity. Each physical parameter must still have valid MIME token/quoted-string syntax. After independent application acceptance, use the authenticated attachment name for display; without an accepted name, use a neutral label.

Only the ASCII-case-insensitive names `filename`, `filename*`, and `filename*` followed by one or more ASCII decimal digits and an optional final `*` belong to this exception. A leading-zero index remains unusable filename metadata. Other names, including `filenamefoo`, `filename*evil` and `filename**`, are non-filename parameters. Process indices within the existing header/parser bounds without allocating by their numeric value; an index that cannot be processed safely leaves filename metadata unavailable.

This exception covers only filename metadata. A missing or repeated Content-Disposition header, malformed header/parameter syntax, a disposition other than `attachment`, or a non-filename disposition parameter still fails this carrier’s selection. Embedded resources still require `inline` without disposition parameters. Resource placement, identifier uniqueness, protected scope, transfer decoding, byte lengths, digests and operation acceptance retain their separate checks and failure outcomes. An unavailable filename cannot repair any of them or authorize a filesystem path, inline rendering or automatic write. Earlier carriers keep their exact receiving rules.

Apply the wrapper’s eight-mebibyte and authored record’s one-mebibyte bounds independently before allocation/decoding, in addition to local bounded MIME/resource/renderer budgets. Base64 inside authored is not recursively interpreted as another record. Complete decoded resource bytes, roles, length and digest checks remain required. Missing/bad resources and well-decoded projection discrepancies retain their owning distinct outcomes; they do not replace authenticated common content, grant access to an unlisted file or authorize a partial structured effect.

Acceptance proceeds through authenticated native sender/context, selected MIME framing, strict envelope6 and exact original authored0, accepted scope/slot mappings, full operation syntax/core relationships and resource-role binding. Compare wrapper principal/conversation/audience to actual independently accepted native evidence; compare authored principal/conversation to the wrapper. Never replace those checks with a verified flag. Missing evidence required for native authority, a complete valid scope or the actual slot map holds application acceptance; that candidate cannot reserve an accepted authored namespace. ### Migration and remaining integration

Establish a fresh ordinary stream or independently admitted managed conversation for this agreement. Keep old in-flight identities, bytes, receiving promises and uncertainty intact. Do not mutate context9 into context10, synthesize assertion10 from earlier evidence, reinterpret old events as logical authored0 records, or copy old live keys/outboxes into the new agreement. Independently authorized local grouping is not history permission; managed migration retains its separate-conversation rule.

An upgrade need not make old correspondence disappear or force the person to stop an already authorized send. Old contexts keep their own processing rules; new messages use an independently selected compatible context. A shared interface can show their relationship without pretending that one protocol record was converted into the other.

8. **Do not downgrade an immutable authored record.** Failure to find the selected agreement holds that secured delivery or follows an independently permitted fallback plan. An older Email/2 structured copy has its own grammar and contribution identity; it cannot masquerade as another envelope6 delivery of the same authored0 record. Ordinary readable and hosted fallbacks retain their exact disclosure/access contracts. Similar text or a local grouping cannot merge their interaction authority, remove mixed-protection status or mark the pending protected delivery successful. Once any copy may have been disclosed, new setup cannot erase that exposure.

Apply the [authored-history mapping](encrypted-archives.md#preserve-messages-that-have-several-deliveries) when exporting or restoring these records. Migration is not a reason to re-encrypt an old archive under its existing immutable artifact identity or discard unsupported records from a claimed complete collection.

## Module agreement and common operation selection

Current assertion10 offers use one fixed readable application per supported ordering, with a separate array of that device's implemented interactions. Select the [exact current offer](#asynchronous-protected-agreement) for every actual selected device. Do not intersect those interaction arrays into a smaller native operation vocabulary. Missing support for a button does not remove its readable question from the conversation.

The sender's independently implemented interaction, deliberate action and current target/authority determine what it may publish. The receiver's independently implemented interaction determines which complete stateful processing and controls it can offer. All clients retain the required safe reading, scope, written-reply and resource checks. Device advertisements are not permissions, online presence or a promise that a person will respond.

The earlier operation-block algorithm below remains exact for v1/v0 compatibility. Its thirty-two subsets and up-to-sixty-four offers are not current assertion10 rules.

::::: {.details summary="Earlier v1/v0 operation-block agreement"}

For the earlier v1/v0 agreements, every Encryption client supports this protected core, including both required HTML/CSS presentation profiles:

Sort offers by ordering, then operation array using ASCII comparison with proper prefixes first. Each mode may support a different maximal optional-module set; there are at most sixty-four tuples. The v1 [assertion9 and control binding](reply-intent.md#reply-aware-protected-agreement) supplies the exact signatures and corresponding ordering-exchange versions. No extra `modules` flag or reply-intent feature boolean supplies missing receiving support.

For an explicitly selected earlier context8 agreement, apply this same operation-block/closure algorithm to its original assertion8 offers with envelopeVersion `"4"` and payload `"mime-suite-v0"`, using that agreement's original control/admission versions. Unsupported operations cannot be repaired by silently changing them into another operation. Ordinary-mail/hosted alternatives follow the independent disclosure policy; semantic conversion requires its own deliberate composition.

An established cryptographic context retains its exact operation set. ## Joining with a simpler client

Clients SHOULD let a person continue a conversation without implementing every optional interaction. Under the current agreement, a simpler client reads the same finite contribution vocabulary and offers the written replies its source permits. A question can remain a question for everybody even when only some clients offer answer buttons.

::: {.details summary="Current simpler-client admission and composition"}

1. Retain the draft, selected account, full intended slots, target and required privacy/reply policy. Select eligible actual devices for the delivery under that policy; never remove a frozen device merely because a feature is inconvenient.
2. Obtain every selected device's original assertion10 and complete offer for the chosen ordering. Their native application is identical; keep their separate interaction lists. Missing or malformed evidence is a hold, not an empty list. Optional interactions do not require a group-wide intersection.
3. Use an existing stream's exact supported agreement and eligible owner admission where applicable. A changed ordinary actual audience needs a fresh independently admitted owner stream. A v1-to-v2 change uses the [migration procedure](#migration-and-remaining-integration), not an edited application or guessed old target. Managed groups retain their immutable application/governance and separate-conversation migration rules.
4. Compose using the local client's implemented capabilities and current authority. A reader without Answers can write a permitted message in response to a readable question; that text is not a structured answer. A reader without Service actions cannot activate a service invitation through a plain link that pretends to be its authorized control. If the person required an exact action the client cannot implement, retain it as unavailable rather than claim it completed.
5. Complete native admission, package/secret retirement, exact carrier and current source/recipient/route/disclosure checks before release. New admission grants no old history. Unresolved targets stay unresolved, and each intended pending recipient retains its own late-delivery obligation.

Software support cannot override a no-replies or private-only source. Adding interaction support later does not replay old controls or convert prior prose into a reaction, structured answer, edit or service result. A deliberate new action uses its own fresh outgoing identity and exact independently eligible target.

:::

The following retained procedure applies to earlier agreements whose optional operations were negotiated as blocks. It cannot be used to reduce the current fixed readable vocabulary or claim that a simpler current reader needs a different question record.

::::: {.details summary="Earlier v1/v0 compatible-stream procedure"}

A client that implements the protected core can exchange readable encrypted messages with clients that implement more interactions. It still implements both required HTML/CSS profiles and the complete Encryption safety rules. “Simpler” means fewer optional interactions, not weaker encryption or partial identity validation.

Clients SHOULD support the compatible composition procedure below. They SHOULD also implement the complete conversation bundle where practical, so questions, reactions and corrections remain usable across more devices. Supporting the bundle is not required for core conformance.

> [!ex] A question becomes a normal conversation
> Alice and Bob previously used answer buttons. Bob adds a core-only device. Alice's client can compose “Tuesday or Wednesday?” as a normal encrypted message in a newly admitted compatible stream. Bob replies “Wednesday” as text. Both contributions appear in their existing ordinary conversation. That text does not submit an answer to an earlier question or call a service.

:::: {.details summary="Compatible composition, admission and failure rules"}

### Establish a compatible ordinary stream

1. Retain the draft, selected sending account, intended audience, conversation, reply target and required protection policy. Resolve the current intended devices through the existing authority and association rules. Do not omit a required device to recover an optional feature.
2. Validate each intended device's current signed assertion and select the common operation set using the algorithm above. Include the sender's participating devices. A missing or invalid assertion is a hold, not an empty optional-module set.
3. If the existing stream's exact agreement is supported by the intended additions, use its normal owner-authorized admission. Otherwise, leave that stream unchanged and establish a fresh ordinary stream with the compatible selected application, fresh stream identifier, fresh MLS group and independently valid admissions. The sender must own the new stream. A device cannot take over another owner's stream.
4. Retain the ordinary conversation identifier only under the locally selected conversation and disclosure context. A private return stream must retain the independently established private pair and delivery roles. Matching a subject, identifier or recipient list cannot establish that authority. A changed audience follows its own fresh-stream/disclosure rules.
5. Apply all current package, membership, freshness, identity, address, routing and release checks. Commit the new admission and preparation under their owning atomicity rules before releasing content. A failed or uncertain setup retains its exact attempt state; it does not authorize a second send, new package allocation under the same attempt or plaintext fallback.

The new stream grants access only under its own admissions. It does not grant old membership, old message secrets or automatic history transfer. Its receiving and retention windows are independently bounded. References to old contributions remain subject to exact target, audience and authorization checks; a missing target stays unresolved.

### Compose readable content without inventing effects

If a draft's intended operation is unavailable in the compatible agreement, preserve the draft and offer compatible composition. The user may choose it explicitly, or a previously selected composition preference may authorize it. Do not require a new prompt for every message. A requirement to use an exact structured operation keeps the draft held.

The compatible contribution is newly composed core content: a `message`, `rich-message` or indexed `reply-message`, with its applicable resources and clear readable wording. It can state a question and choices as ordinary prose. It cannot retain executable answer buttons, reaction controls or service submission controls whose operations are absent. A normal link remains subject to the inert rendering and deliberate navigation rules; it cannot simulate an authorized service action.

Freeze a new contribution identity and exact bytes only after this choice. Do not reserialize a previously submitted event with a different operation under its old identifier. A submitted or uncertain richer contribution retains its original result and retry identity. It cannot be silently replaced with a core message or sent twice through different modes.

A text reply is never a structured `answer`, `reaction`, `edit` or confirmed service result. If a later interaction becomes available, it requires its own supported agreement, exact target and authorized event; it cannot retroactively upgrade that text.

### Reading and managed-group boundaries

A core-only device is not admitted to an old stream whose agreement it cannot implement. Safe readable content reaches it through the new compatible stream or an independently authorized historical export. Previously accepted history may remain readable locally, with its original provenance; unsupported controls stay inert. Diagnostic recovery of an unsupported carrier is not successful protected-event acceptance, and does not prove that the device received the old correspondence.

A managed group cannot change its application in place. Hold an incompatible addition or deliberately establish a separate compatible managed conversation under the [managed lifecycle rules](group-conversations.md#when-a-group-cannot-change). Every intended device must support that managed mode. A device that implements ordinary streams alone cannot be silently placed in a managed group, and a managed conversation cannot be relabeled as ordinary. Local views may associate old and new conversations, but must preserve their distinct audience, authority and history boundaries.

### Creating a delivery and receiving it later

A setup key has one deadline for creating new deliveries and another for receiving deliveries already prepared for it. An offline recipient can therefore open delayed mail within the declared receiving window. Neither deadline deletes correspondence the app has already decoded and retained. Transport acceptance still does not prove that the recipient installed the conversation or read the message.

:::: {.details summary="Exact receiving deadlines, key custody and late admission"}

**Published material.** Assertion8’s receiving-deadline member is `keyPackageReceiveUntil`; its separate required `controlKey` member is defined by the control-encryption contract below. It is `null` when `keyPackage` is empty; with one package it is a canonical unsigned-64 decimal timestamp string. Let `U` be that package's signed `not_after`, and `R` this member. Require `U <= R`; the issuer must retain the unused receiving-only admission secret until `R` unless consumption, explicit withdrawal, revocation or explicit local withdrawal makes it unusable. The issuer MUST persist the exact package reference, original signed package interval and `R` before publication. A copied advertisement or incoming invitation cannot extend that local record. A stricter later policy governs new references; retiring an already published reference early is an explicit withdrawal, not an unreported change of deadline. Republishing the same reference retains the original deadline; a longer deadline requires fresh material and a new reference.

The recommended issuer receive-delay default is 604800 seconds after `U`, independently configurable down to zero or to another finite duration. This is an editorial custody default, not a rotation schedule or a minimum retention obligation. Choose it under local security/availability policy and the relevant credential lifetime. Check addition for unsigned-64 overflow before computing `R`; overflow holds issuance. At `U`, stop issuing the package for new Add proposals and Commits. Retaining the private key for late receiving does not republish it or permit new outgoing setup with it. Exposure from stealing that unconsumed key lasts until its actual retirement, potentially after publication expiry.

**Invitations.** Initial8 and established8 have required canonical unsigned-64 string `receiveUntil`. Bind it to the exact target package reference and its original assertion8. Require `notBefore <= notAfter <= receiveUntil <= keyPackageReceiveUntil`. The original invitation interval must remain inside all creation-time package, assertion, binding and allocation dependencies. A sender's complete credible-time interval MUST be inside that original interval immediately before creating/releasing the admission. `receiveUntil` does not extend source-side Add eligibility, bootstrap authorization, a grant or any other creation deadline. The roster's signed assertion commitments bind the selected target's publication; roster5 needs no duplicate receiving-deadline field.

**Late receiving.** A version8 receiver performs these checks together before installation:

1. Select the exact original signed invitation, common roster or certified path, target package reference and original assertion8. Verify all signatures, package/leaf cryptography, version, suite, capabilities, total-lifetime policy, byte/reference equality and independent creator/context/audience selection. Receiving an expired publication does not make it a currently usable discovery advertisement.
2. Find the exact locally issued package record. It must be unconsumed, not withdrawn and still retained. Require the invitation deadline to fit the original locally recorded deadline. The complete current credible-time interval must be at or after invitation `notBefore` and at or before `receiveUntil`. Unknown time, deadline uncertainty, missing material or a proposed extension holds admission.
3. Verify the original creation intervals against the original signed material, rather than requiring those publication intervals still to contain receipt time. A peer's claimed creation interval is not an independent timestamp or proof of timely transport. No trusted historical signing time is inferred.
4. Independently check current identity, required roles, mailbox associations, verification/freshness policy, current local algorithm support and conversation authorization. Original state references must belong to accepted history. A same-key renewal may establish current authority only through an accepted unrevoked lineage preserving the device, signing key and required role in every intervening state, with overlapping or touching binding-validity intervals; expired current authorization, an unknown branch, a role gap or an unlinked replacement cannot be excused by the receiving window. This is signature/admission validation, not permission to carry an expired provider grant forward.
5. Process the actual Welcome and validate its complete GroupInfo signer, group, epoch, context, membership, proposal/certificate dependencies and target. The only relaxed MLS check is receiving-time leaf lifetime membership in the current time interval. Every signature, parameter, reference and resulting-state check still applies. Recheck the original receiving deadline at the serialized final installation boundary, accounting for elapsed cryptographic work, monotonic time and known clock rollback under the clock contract. Acceptance, consumed-reference tombstone, resulting checkpoint, receipt and secret-retirement intent commit atomically. Complete required retirement before reporting readiness.

[RFC9420 §7.3](https://www.rfc-editor.org/rfc/rfc9420.html#section-7.3) makes the leaf lifetime check mandatory for sent messages and recommended for received messages, expressly allowing for transit delay. This suite selects that bounded receiving exception. It does not disable current account authorization or claim recovery from compromise. An adapter that cannot separate lifetime checking from cryptographic validation MUST hold the input; it must not substitute an unchecked KeyPackage conversion or skip the complete validator.

**Custody and failure.** Unused receiving-only material retires at `R` or an earlier withdrawal/revocation; successful admission retires its initialization secret promptly under MLS's deletion rules. Retries, polling, mail arrival and restart never reset the recorded deadline. No timer can run on a stopped device: after startup, enforce the original deadline before key use. Missing or retired keys leave the original ciphertext retained and the delivery unresolved; they do not authorize plaintext, a different recipient/device, automatic historical disclosure or restoration of live state from an archive. Receiving-only admission secrets remain live decryption capability and MUST NOT be placed in correspondence archives or restored as historical content. Already accepted exact retries return their retained outcome without reusing the old initialization key. Once a message is decoded, its stored history and archives have their separate retention policy.

This rule applies only to the selected assertion8/invitation8 binding. Older encodings retain their stricter acceptance rules. The [timing and actual expired-leaf experiment](evidence/README.md#bounded-delayed-admission) is component evidence; complete signed version8 publication, custody, current-authority and release integration remains required.

### Unread mail and long offline periods

A person does not have to open a message before its setup key expires. While the enabled client can access the mailbox, it processes eligible encrypted mail into protected local correspondence without marking it read or sending a receipt. Unread correspondence then has the same retention as read correspondence. A human reading deadline must not be substituted for a cryptographic receiving deadline.

If every eligible device stays offline beyond the retained keys’ deadlines, an unopened delivery may need a separately authorized historical copy from a surviving device or correspondent. Fresh setup makes future delivery possible; it cannot recreate deleted secrets or recover that old ciphertext by itself. The client preserves the unavailable delivery and distinguishes recovery from a new message.

:::: {.details summary="Processing stages, availability policy and recovery outcomes"}

**Separate stages.** Mailbox presence, authenticated control decoding, MLS admission, authenticated application decoding, retained correspondence and human reading are separate states. An SMTP acknowledgement or IMAP arrival is not any later state. The receiving client MUST preserve the original ciphertext or its independently retained mailbox location and its unresolved reason under the disclosed mailbox/local retention policy when processing cannot complete. This is not permission for unbounded storage or processing; unavailable/evicted source bytes remain an explicit loss. It must not display an empty conversation as though that mail never existed. Hostile or undecryptable outer mail cannot establish an author, thread, recipient or trustworthy historical selector.

| Retained state | Required behavior |
| --- | --- |
| Only outer control ciphertext | The original control key must still be retained and eligible at the whole credible-time interval of decryption. Its expiry is not extended by mailbox arrival or an asserted send time. |
| Authenticated decoded invitation, not installed | The original invitation/target package and receiving deadline still govern admission. Retaining the decoded public proofs does not preserve missing private admission material or bypass the original invitation deadline. |
| Accepted MLS instance, application not yet decoded | The initial package/control deadlines no longer time this instance. Process under the applicable installed context, current effects policy and unconsumed MLS secret-retention rules. Do not reuse the consumed initialization key. |
| Authenticated application durably retained, still unread | Retain correspondence under its independent history policy. Retire consumed transport secrets on their normal schedule. Neither expiry nor cleanup marks it read, sends a receipt, submits an answer or removes its readable content. |
| Required unconsumed material retired or lost | Preserve unavailable ciphertext and explanation. Reconnection, a fresh advertisement or a new Welcome cannot decrypt it. Use only an eligible historical recovery path below. |

**Availability policy.** Before publication, an implementation selects and retains an explicit maximum intended offline/delivery interval as part of trusted local availability policy. This is an implementation setting, not a new assertion field, a mandatory universal duration or a promise made by a sender's header. Its publication, control-key and package receiving windows must be planned together. A new delivery's effective setup receiving limit is the earliest of its invitation deadline, original target package promise and selected control-key promise; later installed application secrets have their own bounds. Current account/device authorization, withdrawals, compromise, mailbox access and processing-resource limits remain independent prerequisites. Do not advertise an unconditional offline-readability guarantee based solely on those timestamps.

Automatically renew and process eligible mail while authorized mailbox access and protected storage are available, including when the person has not opened the conversation. Background eligibility does not require sending presence or read notifications. When the platform cannot execute in the background, show that limitation in the available offline/recovery explanation; do not claim that operating-system suspension performed decryption. Before deliberately shortening an existing promise, follow explicit withdrawal and expose the resulting availability loss. Never silently keep expired live keys, recover consumed ancestors, or extend a published window merely to satisfy an availability target.

The current engineering defaults remain configurable recommendations, not a statement that a week is enough for everyone's email. Clients must make the selected offline/recovery boundary discoverable before users rely on it and show when a delivery needs recovery. No ordinary message timer deletes retained readable correspondence. A provider's ciphertext mailbox and a readable-history archive are different recovery resources.

**Recovery selection.** First look for independently retained accepted correspondence belonging to this local account, or an explicitly selected complete/incomplete archive under its own pinned verifier and recovery material. An archive contains only what an authorized source actually decoded and exported; a backup taken before that mail was processed cannot supply its missing plaintext. Import remains historical and cannot activate the old message's answers, corrections, reactions, outbox or membership state.

If no local historical copy exists, the client may offer an existing authorized device or a known correspondent's [history transfer](history-transfer.md). Use that contract's exact request, current identities/roles, separately approved source scope, recipient-selected fresh archive encryption and inert import. If only a sealed-control attachment remains, use its [exact opaque-delivery selector](history-transfer.md#recover-an-unopened-delivery) inside the confidential request to an independently known source. The selector cannot identify a trusted correspondent or authorize history by itself; unknown sources and missing original mappings remain unavailable. Original addressing alone is not a history grant. A remembered policy may authorize a specific transfer only when it genuinely covers the exact retained scope and current target; no new universal automatic-disclosure permission is inferred. A control record, unknown relay alias or message preview cannot supply a trusted recovery service or callback. An unavailable or expired original source may be unable to help; retain that outcome rather than pretending a fresh cryptographic handshake restored history.

A historical copy preserves its source provenance and original event references. It must not become a second live contribution or trigger effects merely because the original encrypted carrier remains unavailable. A deliberate newly authored resend uses a fresh event and normal current audience/disclosure checks; it is distinguishable from a historical import. Repeated recovery and an eventual genuinely accepted original cannot create duplicate effects; use the existing exact-event/resource commitment and provenance/conflict rules. Future sending separately uses current admission, never imported live state. A newly enrolled device acquires no automatic history entitlement, and this protocol does not choose a product's price or storage subscription.

**Acceptance.** Exercise background authenticated processing with no human read/receipt; unread retained content after original setup and transport-secret expiry; all-devices-offline delivery within and beyond each independent receiving bound; loss of keys before expiry; clock uncertainty and restart; shorter control versus package windows; actual missing-key/deleted-secret failure; archived history present versus a snapshot preceding the message; exact authorized historical import without live effects; unavailable/expired/revoked transfer sources and targets; duplicate recovered/original content and conflicting bytes. Evidence must distinguish a selected design and component tests from a joined current-suite availability implementation. [RFC9750 §6.3](https://www.rfc-editor.org/rfc/rfc9750.html#section-6.3) requires asynchronous transport; [§7](https://www.rfc-editor.org/rfc/rfc9750.html#section-7) identifies retention and reordering parameters that applications must define. Email/2 selects the bounded lifecycle plus separate historical-copy recovery; it does not claim MLS reconstructs destroyed secrets.

## Confidential setup and control

Invitations and key updates can themselves contain personal addresses. Email/2 encrypts those protocol objects for the intended device before putting them in mail. A relay therefore receives an opaque carrier, not a readable copy of the setup proofs. The original signatures remain inside and are still checked after decryption.

Each device publishes a separate, expiring control-encryption key with its signed setup. It is not an account password, an MLS group key or a backup key. Remembered setup policy can manage it automatically. A missing or expired key holds the affected control delivery; it does not permit a readable replacement or a misleading address-masking indicator.

:::: {.details summary="Exact sealed-control format, recipient keys and lifecycle"}

**Selected construction.** `sealed-control-v0` uses [RFC9180 §6.1](https://www.rfc-editor.org/rfc/rfc9180.html#section-6.1) single-shot HPKE Base mode with KEM `0x0020` (DHKEM X25519/HKDF-SHA256), KDF `0x0001` (HKDF-SHA256), and AEAD `0x0001` (AES-128-GCM). These are the HPKE components already selected by the MLS suite, with a separate recipient key and application context. No PSK, Auth-mode substitution, exporter-only mode, alternative algorithm or trial decryption is selected. Base encryption does not authenticate a sender; the signed intent and original owning protocol do that separately.

**Advertisement.** Assertion8 has required `controlKey`. Its value is either null, or exactly `{id,publicKey,notBefore,notAfter,receiveUntil}`. `id` is a freshly random nonzero ObjectId; `publicKey` is 32 X25519 public-key octets as 64 lowercase hexadecimal characters. Apply RFC9180 public-key validation through the cryptographic implementation, including rejection of invalid/all-zero shared-secret inputs. The producer uses canonical X25519 serialization; noncanonical encodings are not repaired. All times are canonical uint64-string seconds, with `notBefore <= notAfter <= receiveUntil`. The assertion's whole publication interval fits the key's publication interval, which fits the issuer's accepted binding interval at issuance.

A nonempty MLS `keyPackage` requires a nonnull control key. An advertisement with no MLS package may still provide a control key for already admitted conversation traffic; both absent is a capability claim, not usable setup. The exact assertion8 receiving promise and this key descriptor are independently signed as part of the original assertion. The null exception applies only to these explicitly named root fields, not ordinary contribution events or other nested values. All Encryption clients support this container as part of the same agreement; no unadvertised weaker transport is inferred.

Generate fresh independent control key material; never convert, reuse or restore an MLS initialization/group key, device-signing key, route key, pairing key or archive identity for this role. Persist the exact device/key ID, public key, original publication/receiving intervals and private-key custody before advertising. IDs are unique across the receiving client's retained control-key inventory. Collision or ambiguous ownership holds the affected publication/input; do not try several keys or overwrite an existing owner. Reusing a key under another ID or device is not renewal. Republishing the same key retains its original deadlines; renewal generates new material and a new ID. Before publication, verify possession through the selected local cryptographic store.

A recommended configurable maximum publication lifetime is 604800 seconds, bounded by the applicable credential. The independent recommended receiving delay after publication expiry is 604800 seconds; zero or another finite duration can be selected. These are engineering defaults, not a fixed rotation frequency or mailbox-storage quota. A stricter later policy governs new material. Early retirement of an already published key is explicit withdrawal/revocation rather than an undisclosed shorter promise. Check all timestamp arithmetic for uint64 overflow.

**Outer binary.** Transfer-decoded bytes have exactly:

```text
8 octets "EML2CTL0"
16 octets recipient control-key ID
32 octets HPKE encapsulated key
4 octets unsigned big-endian ciphertext length
that many ciphertext octets (including the 16-octet AEAD tag)
```

There are no trailing bytes, clear sender/recipient principals, personal addresses, conversation IDs, algorithm selectors, compression, a separate plaintext-length field or unencrypted proof copies. Ciphertext length still reveals frame length. The header's key ID is an opaque lookup hint, not authority. Construct HPKE `info` as ASCII `email2/sealed-control/v0`, NUL, the 16 raw key-ID octets and the selected 32 public-key octets. `aad` is the eight magic octets, the same key ID and the four ciphertext-length octets, in that order. The encapsulated key is bound by HPKE's KEM context. For this suite ciphertext length is plaintext length plus sixteen. Use the cryptographic implementation's fresh encapsulation; never reuse a context or nonce for another encryption.

**Encrypted frame and signature.** Plaintext has exactly eight ASCII octets `EML2CIN0`, a U32 big-endian intent length, the exact UTF-8 intent bytes, a 64-octet Ed25519 signature, a U32 big-endian identity-bundle length and those exact JSON bundle bytes. No padding or trailing data is defined in this version. Maximum plaintext is 8,388,608 octets; the original body below is at most 4,194,304 and the bundle at most 1,048,576. Existing stricter owning-protocol limits still apply. These are bounded wire-processing limits, not storage quotas; an implementation unable to complete processing reports unsupported size without truncating or accepting a prefix.

The strict intent object has exactly `{version,purpose,record,sender,recipient,key,kind,body,notBefore,notAfter}`. Version is `"0"`; purpose is `"sealed-control-intent"`; record is a fresh ObjectId. Sender is `{principal,device,state,binding}`; recipient is `{principal,device}`. `key` is the same control-key ID. `body` is canonical padded base64 of the complete original transfer-decoded owning control/admission JSON bytes. Retain those original bytes, including their own signatures and references. `notBefore` and `notAfter` are canonical uint64-string creation/release bounds. Sign the original intent bytes with the sender's accepted device key using domain `email2/sealed-control-intent/v0` and the existing NUL/U32-length framing. The identity bundle supplies candidate records, never a new trust anchor by receipt alone.

Kinds are exactly `initial-invitation`, `established-invitation`, `stream-control`, `stream-recipient-update`, `quorum-exchange`, `quorum-control`, `identity-admin`, `history-request`, `history-grant`, `history-receipt`, `history-source-cancel`, `history-target-cancel` and `mailbox-setup-response`. The last kind uses current receive authority and the [exact ordinary-mail setup response](mailbox-setup.md#encrypt-the-response-then-establish-the-conversation), bound to its original pending initiating request and selected control key. It cannot authorize an application send or elicit another response. Identity-admin uses the [state1 proof-circulation contract](identity-state.md#concurrent-administration-and-retirement) and its [narrow confidential-recipient selection](identity-state.md#select-a-confidential-repair-recipient): its body is one exact bundle1 or repair-share1, and its branch-scoped source authority can authorize administrative proof circulation during a conflict, never application sending or operational grants. The [terminal-notice case](identity-state.md#deliver-a-retirement-proof-without-reopening-the-account) permits only an already committed, frozen retirement proof to circulate after its signer retires, with exact predecessor binding and separate transport authority. The five history kinds use the [exact history actor/carriage binding](history-transfer.md#carriage-and-file-retrieval), preserving original signed record bytes and independently approved artifact scope. Requests/receipts/target cancellations use the target’s receive role; grants/source cancellations use the source’s send role. A terminal result does not bypass control-key, route or transport authority. All other kinds keep the role and owning checks below. Each selects its already defined current-suite schema; no parser tries older versions after a failed current validation. The wrapper sender is the invitation creator, source owner or update proposer for the corresponding first four kinds. For quorum traffic it is a currently authorized publishing member under the owning quorum contract. A provider or arbitrary recipient cannot re-sign as that actor. Account/SMTP/relay operation permissions remain independently required; a receive-role key-update privilege cannot create a transport send grant. Original signatures/native MLS validation remain required; the wrapper signature never substitutes for a vote, membership transition or mailbox association.

**Preparation and release.** Resolve the intended device and original signed assertion through the existing account/association/freshness policy. Only identity-admin may use the explicit branch-scoped recipient-key procedure above during its own pinned conflict; a generic sealed-control parser or another kind cannot select that exception. Check the control key's exact publisher and independent recipient selection before encrypting: the inner recipient, the selected assertion actor and the control-key owner must be identical. A decryption-time mismatch cannot undo disclosure to a wrongly selected public key. The complete credible creation/release interval must fit the intent, original key publication and required sender/recipient authority intervals. For an invitation, its declared receiving deadline also fits both the target's MLS package promise and this selected control key's receiving deadline. Preserve every stricter original-body deadline; repacking cannot reset it.

Sign and encrypt once, then atomically retain exact intent/signature, selected key/authority/association dependencies and original ciphertext in the outbox before exposing bytes. Retries use that ciphertext. Replacing an expired recipient key requires a separately revalidated preparation for the same actual recipient and original owning object, never silently new membership, another device or a longer original validity. Owning object identities prevent duplicate effects across separately encrypted copies. For a frozen terminal notice, the owning terminal-only permission replaces operational sender eligibility; every other release dependency remains required. Database commit is not atomic remote delivery; transport uncertainty retains its explicit retry rules.

**Receiving.** Bound and parse the complete outer binary before allocating or invoking cryptography. Select exactly one locally issued, unwithdrawn key by ID; verify its retained owner and full credible-time interval through `receiveUntil`, accounting for elapsed work and known clock rollback. Unknown or retired IDs remain unresolved controls, not prompts to export keys or automatic replies. Decrypt fully and authenticate the final AEAD tag in private staging before parsing any intent. Check exact inner framing, signature, actor binding, recipient and selected control key, kind and original creation bounds. Original publication may have expired during transit; current source/recipient authority and the unchanged key promise still apply. The validated terminal-only identity-admin case checks its exact predecessor/retirement authority instead of requiring the retired signer to remain operational; it never activates that signer or another body kind. For this delayed receipt, the original sender binding can survive accepted continuous same-device/key/role renewal with overlapping or touching intervals under the [purpose-specific continuity rule](provider-grants.md#continuity-and-freshness-have-different-scopes). A role/key/revocation gap holds; original creation bounds still fit the original binding, and the owning protocol may impose a stricter requirement. An old claimed signing time cannot excuse a known revocation or role gap.

Then invoke only the selected owning validator on original body bytes. It checks native MLS/Welcome, stream or managed mode, group/target, mailbox/route, disclosure and complete proof dependencies. The actor and intended recipient must match the sealed intent and actual local delivery scope. A forwarded invitation cannot enroll its holder as the original target. No plaintext/rendering, action, key consumption or group publication follows from HPKE success alone. Missing evidence stays pending and does not install a peer identity.

An identity repair is the explicit fresh-authorization boundary in the state1 contract. The delayed-control same-key renewal exception does not carry an earlier live permission across that boundary.

Retain intent identity as `(sender principal, sender device, record)` and immutable original bytes/signature. Different ciphertexts containing one exact signed intent are duplicate carriers, not a new event or a source fork. Differing authenticated intent bytes under one identity are conflict evidence. Atomically couple the accepted receipt to owning admission/control effects and their existing IDs; a fresh envelope cannot replay an already accepted invitation, update, vote or transition. Malformed ciphertext and unsigned substitutions cannot poison authenticated identity/conflict state.

A control key can decrypt several separately encapsulated controls until its original deadline; it is not consumed by one Welcome. Retire it on its declared deadline, explicit withdrawal/revocation or device retirement under the secret-custody contract. Timers cannot run on a stopped device: enforce expiry before use at startup. Store keys through supported OS-protected secret storage; they are not password-sync enrollment authority, QR configuration, correspondence archives or restore material. This container has no forward-secrecy guarantee against later theft of a still-retained control key. It protects metadata while MLS separately protects conversation content; deletion/storage limitations and non-post-quantum limits remain explicit. Already decoded correspondence does not expire with the control key.

**Mail and relay binding.** Proposed unregistered outer media type is `application/vnd.email2.sealed-control`, without parameters, using canonical MIME base64. No personal subject, address-bearing notification, filename, duplicate readable proof, nested activation or external retrieval is included. No new HTTP carriage operation is selected here. Use the defined mail carrier or hold unsupported transport; providers do not become decryption endpoints.

Never try that parser or clear carrier as recovery from a failed sealed control.

Obtain control keys through valid cached setup, an already protected exchange, the authenticated bootstrap service or the explicitly permitted initial [mailbox setup request](mailbox-setup.md); never reflect mailbox-bearing advertisements into clear masked mail to bootstrap this container. Public advertisements use only channels permitted by the selected disclosure policy. Required sender/recipient masking holds when either route projection or confidential control carriage is unavailable. The format does not promise provider anonymity, invisible account existence, size hiding or unlinkability of a key ID during its lifetime.

This layer deliberately seals setup objects separately from human-message presentation. ## Ordinary protected conversations

Each sending device owns its own encrypted stream. Alice's laptop, Alice's phone and Bob's device can therefore send independently while their contributions form one conversation. A newly enrolled device starts a fresh stream from valid recipient setup; it does not copy another device's live encryption state or wait for other participants to vote. If required setup or account authority is unavailable, its delivery waits under the existing setup policy.

A stream's owner controls that stream's cryptographic membership, not the conversation or anyone else's stream. Ordinary email keeps per-message audiences. A changed audience gets a freshly admitted stream and does not grant access to earlier messages. A managed group instead selects shared membership and the existing quorum contract explicitly. The two modes cannot be substituted for one another after a conversation is established.

:::: {.details summary="Exact ordinary-stream negotiation, admission and state transitions"}

This application-level ordering choice follows the MLS conflict-prevention boundary in [RFC9420 §14](https://www.rfc-editor.org/rfc/rfc9420.html#section-14) and the separate-group model in [RFC9750 §6.2](https://www.rfc-editor.org/rfc/rfc9750.html#section-6.2). The source ownership and conversation-graph rules below are Email/2 requirements, not claims that MLS already defines this email model.

**Agreement.** Every Encryption client supports `sender-stream-v0`. It may additionally support `endpoint-quorum-v0` for managed groups. Assertion8's application array is sorted by `(ordering, operations)` using ASCII comparison; operations arrays retain the prefix rule above. For each advertised ordering independently, include its complete optional-module subset closure. Ordinary-stream support is required; managed support and its optional module set are independent. At most sixty-four tuples are possible. Select the ordering from authenticated local compose/group intent, then intersect modules only among that ordering's tuples for every intended device. Absence of the selected ordering holds establishment; support under another ordering cannot supply missing operations.

For ordinary context8 the ordering object is exactly `{kind,stream,owner}`. `kind` is `"sender-stream-v0"`; `stream` is a fresh nonzero ObjectId. `owner` is exactly `{principal,device,signingKey,state,binding}` under the existing identifier/key/digest grammars. It names the initial creator's exact device, key and accepted birth evidence. Administrators are exactly `[owner.principal]`. The owner's other devices cannot take over this stream. Same-device/key binding renewal requires accepted continuous authority under the existing lineage and clock rules; a new key, device or role gap requires fresh stream admission.

All other context8 fields, application, required rendering, delivery and private-copy rules remain mandatory. For the original private-copy establishment the owner is the delivery originator. A later ordinary return stream may instead be owned by an authorized device of the private recipient, retaining the same independently selected two-principal delivery object and conversation under the [private-reply admission rules](private-copies.md#private-replies-in-the-current-agreement). Delivery originator and per-stream owner are distinct roles; an incoming invitation alone cannot establish the preexisting private relationship. The original signed roster fixes that stream's principal audience and delivery role. Additions can add devices of those principals only; removing the last device of a required principal holds further content until suitable fresh admission is available. A different principal audience or delivery role requires a fresh stream under independently selected compose/disclosure intent. An ordinary conversation identifier is a grouping identifier, never membership authority or permission to read prior content.

**Initial admission.** Initial8/roster5 retain their exact field sets and signatures. In ordinary mode `roster.creation` equals `context.ordering.stream`; the creator identity/state/binding equals the owner’s corresponding values, and the sole creator member’s signing key equals `owner.signingKey`. Independently select the actual creator, intended principal/device inventory, canonical mailbox associations and exact context. Every selected device advertises the chosen ordinary tuple. Validate every actual package, original signed proof, complete Welcome reference set, GroupInfo signer, finalized full GroupContext and actual roster. Apply the declared receiving window and atomic package-consumption/retirement procedure. There is no witness list or quorum certificate in this branch.

Retain stream identity as `(owner principal, owner device, stream ObjectId)` together with its distinct MLS GroupId and the existing common-roster `genesis` anchor. An equal ObjectId from another owner is not the same stream. A GroupId/anchor collision cannot replace an accepted binding. Different completely validated signed births for the same full owner/stream identity are retained as binding conflict and hold that source’s new effects. Independently authorized streams may name the same ordinary conversation; that grants no cross-stream cryptographic authority. A shared subject, outer Message-ID, participant list or guessed conversation identifier cannot select or change the local acceptance policy. Remembered contact, setup and compose policy can authorize routine stream establishment automatically; independent validation does not require a new per-message approval dialog.

**Owner transition.** Only the exact stream owner may author an accepted Commit. Its signed transition payload has exactly:

```text
{version,purpose,owner,stream,genesis,group,previous,
 predecessor,result,commit,updates,members,applicationAssertions,
 notBefore,notAfter}
```

Version is `"0"`; purpose is `"stream-transition"`. `owner` is `{principal,device,state,binding}` identifying the same immutable owner key through accepted identity evidence. `stream` and `genesis` name the retained birth. `group`, `predecessor`, `result` and `commit` are canonical padded base64 of, respectively, exact nonempty MLS GroupId bytes, full predecessor GroupContext, full resulting GroupContext and the actual MLS PrivateMessage Commit. `previous` is `"genesis"` for the first transition, otherwise the previous transition ID. Epochs must advance by exactly one; every other immutable application/owner/delivery field stays unchanged. The result's full GroupContext, not an epoch number alone, is compared.

`members` is the resulting roster, uniquely sorted by principal/device. Each entry is exactly `{principal,device,signingKey,state,binding}`; actual native credentials/keys must match, and referenced authority must be accepted independently. `updates` is an ordered array of `{digest,signature}` references to the original signed recipient-update payloads described below, sorted by digest. No duplicate actual MLS ProposalRef is allowed. `applicationAssertions` is the existing ordered `{principal,device,digest,signature}` reference array for precisely the actual Add proposals. Its complete assertion8 wrappers must match the actual added package bytes, KeyPackageRefs and unchanged application agreement. No-Add/Update transitions use empty arrays.

The transition wrapper is exactly `{payload,signature,identity}`: original payload bytes in canonical base64, lowercase hexadecimal Ed25519 signature and the owner's identity bundle. Sign with domain `email2/stream-transition/v0` under the existing NUL/U32-length framing. Its transition ID is SHA-256 of `email2/stream-transition-id/v0`, NUL, U32 payload length, original payload bytes and the 64 signature bytes. Incoming bundles supply candidates; they never replace retained pins. The canonical uint64-string interval must fit the source's creation-time authority and all selected Add/update dependencies. Check the whole credible interval at construction and final release. A claimed creation interval is not a trusted historical timestamp.

The control carrier has exactly `{version,purpose,transition,updates,applicationAssertions,identities}`. Version is `"0"`; purpose is `"sender-stream-control"`. `transition` is the signed wrapper above. Unknown fields, partial arrays and mixed mode/version proofs do not produce a partial change. Removed credentials must match the authenticated predecessor but need not retain receive authority; current receive authority is required for every resulting endpoint, and current send authority for the exact owner. Otherwise revocation could prevent its own necessary removal.

Permitted Commits are owner self-updates, accepted recipient Updates, Add/Remove and their combinations, with complete actual proposal inspection. Context/delivery/application changes, external joins, PSKs, ReInit, subgroup creation, owner replacement and stream-wide closure are unsupported in this mode. An unsupported authenticated transition is retained and held, never partly installed. Changed audiences use a fresh ordinary stream; changing to a managed group requires a distinct conversation identity and explicit new admission.

**Recipient repair.** A non-owner member can supply fresh leaf material without voting on ordering. Its update payload has exactly `{version,purpose,request,proposer,owner,stream,genesis,group,predecessor,proposal,notBefore,notAfter,receiveUntil}`. Version is `"0"`; purpose is `"stream-recipient-update"`; `request` is a fresh ObjectId. `proposer` is `{principal,device,state,binding}`; `owner` is `{principal,device}`. The uint64-string validity interval governs creation/release and owner Commit creation. `notBefore <= notAfter <= receiveUntil`; the last is an immutable, locally recorded receiving deadline for the exact fresh Update secret. Apply the bounded custody, elapsed-time, withdrawal and no-archive rules used for admission secrets. Reissuing the same proposal cannot extend its recorded deadline. A fresh proposal requires fresh private material and a fresh request. An accepted nonempty proposal retains MLS's send hold until an authenticated owner transition commits it or removes that exact proposer leaf with a retained disposition; expiry, polling, a timer or restart cannot clear that hold. There is at most one outstanding recipient update per leaf and predecessor. A second different valid request is retained as conflict, not resolved by arrival order. Serialize all compatible accepted Updates together with the owner's membership plan; a removed leaf's request is recorded as superseded by that removal. An unrelated empty self-update cannot discard pending requests or bypass their hold. With valid material the owner can commit asynchronously without recipient ordering votes. Merely receiving unverified mail creates no hold or response. Missing or unusable dependencies stay pending. An irreparable old stream can stay held while a fresh, independently admitted ordinary stream is created from current eligible material; the old checkpoint is never restored or relabeled.

Owner self-updates alone do not repair a copied recipient state. Repair requires that recipient's fresh contribution in every affected stream, or fresh independent admission using uncompromised material. Public updates in another stream and packages stolen before remediation do not establish recovery. Revocation/rebinding remains necessary when an attacker retains signing authority.

**Serialized installation and equivocation.** The owner signs one immutable transition record per actual Commit and commits the successor, original signed transition, advanced sending state and immutable control/Welcome outboxes together before exposing bytes. Authority renewal and additional proof supplements do not rewrite that signed record; a different signed record for the same Commit is an immutable-record conflict. Concurrent local writers serialize; retries return exact retained bytes. A failed transaction exposes no candidate. Neither a received secret checkpoint nor an old captured predecessor is an installation input.

A recipient processes the actual Commit and referenced proposals against its exact predecessor in private staging, validates owner, full result/roster, original signed dependencies and current authorization, then atomically installs checkpoint, transition receipt, membership episodes and retained dependency evidence. No application effects run while staging. Missing predecessors/proposals remain pending. Late catch-up may traverse authenticated intermediate revoked rosters only in recovery staging; no outgoing content, promotion or action is allowed until a fully current authorized final state is reached. The owner's immutable key must have continuous accepted send authority; this is not a revocation bypass.

Two completely validated owner-signed successors of one predecessor are retained as conflict evidence and hold new effects for that source. Duplicate carriers of one exact transition are not forks; malformed or substituted supplements cannot poison the stream. No first-arrival, largest epoch, timestamp or SMTP outcome selects a branch. Previously accepted history remains available. The mode provides owner sequencing, not Byzantine agreement among isolated recipients; the managed quorum guarantee remains distinct. An unavailable owner disables privileged changes to its stream without blocking other authorized owners' streams.

**Established admission.** Established8 retains its field set and receiving deadline.
